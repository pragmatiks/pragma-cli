# Commands

The behavior contract of every `pragma` command: arguments, output, errors and exit codes. Change it in the same commit as the command.

## Resources
- `pragma resources list [--provider|-p <p>] [--tag <t>]... [-o json|yaml]` - List resources with optional filters
- `pragma resources schemas` - List available resource schemas
- `pragma resources get <org/provider/resource[/name]>` - Get resource(s) by type or full ID
- `pragma resources describe <org/provider/resource/name>` - Show detailed resource info; a `Health` row after State shows the resource's `health` (`healthy`, `blocked`, `failed`, or `degraded — <id> failed`, naming every failed dependency in `degraded_by`, comma-separated), an `Owned by:` section shows its `owner`, the resource that applied it and whose deletion deletes it, as `  <provider>/<resource>/<name>` followed by the owner's `command` dimmed, and a `Blocked by:` section lists each of its `blockers` as `  <id> — <reason>` followed by the blocker's `command` dimmed (an owned resource that failed reads `<id> failed. Apply this resource again to retry it.`), and a `Waiting for provider:` section shows its `provider_blocker`, set while the resource's provider changes version, as `  <provider> — <reason>` followed by its `command` dimmed; each is left out when the API does not send it; a `Provider version` row after `Operation` shows the provider version whose operation produced the outputs, left out when the API sends none
- A processing resource holding a configuration applied while its operation runs (`queued_config`) shows its state as `processing (apply queued)` in the `list`/`get` State column, the `describe` State row, the `apply` `Applied <id> [<state>]` line and the `PARTIAL APPLY FAILURE` report's applied list; `describe` also shows an `Operation` row, `<operation type, lowercased> <operation_id>`, while the resource carries an `operation_id`
- `pragma resources apply <file>... | -f <file>... [--draft]` - Apply resources from YAML. Every document is sent as `pending`, or as `draft` with `--draft`, whatever its own `lifecycle_state`; the API refuses a draft save of a resource that is neither new nor a draft (409, its message names the recovery). While a provider moves its resources to a new version (installation state Translating), the API refuses an apply or a draft save that writes a resource of that provider with a 409 that the global handler prints unchanged; it names the provider and the target version and ends with the action to repeat, for an apply `<provider> is moving its resources to <version>. Apply again once pragma providers list --installed shows <provider> ready.` Files given both positionally and with `-f` are a usage error. Every document is planned first; invalid documents are listed and the command exits with an input error before anything is applied. A schema read the API refuses (any status but 404, which skips schema validation for that provider), a schema that is not a valid JSON schema, or a broken network goes to the global handler, failure, before anything is applied
- `pragma resources delete|deactivate <org/provider/resource/name> | -f <file>...` - Delete or deactivate a resource. With `-f`, every file is parsed and checked first; a file that is not UTF-8 or valid YAML, or a document without a provider, resource and name or declaring a `project_id` other than the active project, is listed and the command exits with an input error before any resource changes. A resource ID together with `-f` is a usage error. The response's impact prints under `Resources this reaches:` as one `  <id> (<state>) — <action>` line per resource reached, `<state>` being the state it is in before the teardown and `<action>` one of `torn down`, `left in draft`, `moved to waiting until its dependency returns` or `failed, its dependency is deleted`; `--dry-run` prints `Dry run — <id> was not removed.` (or `was not deactivated.`) above those lines and changes nothing, and a refused preview prints the API's message and fails as the real call would
- When `--project` or `PRAGMA_PROJECT` sets a project other than the context default, every project-scoped resource command first prints `Using project '<project>' (source: --project flag|PRAGMA_PROJECT env var; context '<context>' default is '<default>'|none set)` on stderr; with the context default, or an override naming the same project, nothing extra is printed, so the notice has no suppression switch
- `pragma resources tags list/add/remove` - Manage resource tags; `add` and `remove` take `--tag <t>` (repeatable)
- No subcommand option uses a short flag the root command uses (`-c` for `--context`, `-t` for `--token`); `--tag` and `providers install --config` have no short form
- A resource ID that is not `org/provider/resource/name` with no empty segment (`get` also takes `org/provider/resource`) is a usage error before any request

## Providers
- `pragma providers list [--installed] [-o json|yaml]` - List providers in the store; `--installed` lists installed providers with columns Provider, State (labelled as on the web: Queued, Starting, Draining, Translating, Switching, Running, Failed, Uninstalling), Version (served, a dash before the first ready), Operation (the running operation and its target version, `restart` for a host start, while `operation_running`, a dim dash once it settled) and Message (the failure message); JSON/YAML records carry `installed_version`, the raw `lifecycle_state`, `operation_type`, `operation_version`, `operation_running` and `failure_message`
- `pragma providers init <name> [--directory|-d <path>] [--description <text>] [--author <name>] [--email <email>] [--defaults]` - Initialize a new provider project in `--directory` (default `./<name>-provider`); `-o`/`--output` is not accepted, and `--description` has no short form. The `Creating provider project:` and `Template:` lines and the blank line after the copy go to stderr; stdout carries the `Created provider project:` line and the next steps
- `pragma providers update [project-directory]` - Update project from template
- `pragma providers publish [project-directory | --wheel <path>] [--changelog <file>] [-o json|yaml]` - Publish a new provider version: builds the wheel with `uv build --wheel --out-dir <project-directory>/dist` (so a uv workspace member's wheel lands in its own `dist/`; a project directory that does not exist or has no `pyproject.toml`, a missing `uv`, or a failed build is an input error) unless `--wheel` points at a prebuilt one (passing both is a usage error). All its progress goes to stderr and, in table format (the default), only the final `Published <name> <version> — Python …, SDK …, <n> resource types` line goes to stdout. Once the wheel is built it reads the caller's organization behind a spinner (`GET /organizations/me`, refusals go to the global handler), renames a copy of the wheel behind a `Renaming <filename>...` spinner to the organization's distribution name `<organization>-<provider>` in a `pragma-publish-` temporary directory kept until the upload ends (`pragma_sdk.rename_provider_wheel`; the original file is left unchanged; a wheel already carrying that name, or naming no single provider, is used as is) and prints `Renamed to <filename>` when the filename changed, reads the version's declaration from the renamed copy behind a `Reading <filename>...` spinner (a wheel that cannot be renamed or read, a wheel expanding past the size limit included, exits 2; a built wheel whose reading fails with an operating system error once open prints "Could not read the wheel: <reason>. Check the disk holding the wheel, then publish again.", input error; a renamed copy, or its temporary directory, that cannot be written, or a renamed copy that cannot be read back (an operating system error opening or reading it), prints "Could not write the renamed copy of the wheel: <reason>. Free space in the temporary directory or point TMPDIR elsewhere, then publish again.", failure; the temporary directory is made before the CLI knows whether a copy is needed, so one that cannot be created fails a wheel needing no copy too; a temporary directory that cannot be removed prints "Warning: Could not remove the temporary directory <path>; delete it yourself." and never fails the publish). The organization is read before the wheel, so an unreachable API is reported before an unreadable wheel. It then declares the renamed copy with `POST /providers/publish` (201 new, 200 when the identical declaration is already in flight) and prints `Publishing <name> <version>` and the operation id dimmed. When the declaration returns a `wheel_upload` address (only while the version is `awaiting_wheel`) it PUTs the renamed copy straight to that signed storage address and prints `Uploaded <size>`, or `Wheel already uploaded` when storage already holds it; the watch spinner then starts at `wheel uploaded, waiting for Pragmatiks to record it`, the label it keeps while reads still show `awaiting_wheel`. Without an address it prints `Wheel already received` and a `Status: <label>` line for the declared status, and the spinner starts there. It then polls `GET /providers/{name}/versions/{version}` every 2 s from the declared version, showing the status label beside a spinner and printing a `Status: <label>` line each time a read shows a different status from the previous one, until the organization's provider host admits it (`published`) or fails it (`failed`, prints the version's `error_message`, failure). The wheel alone identifies the version: its `pragma.provider` entry point names the provider and its metadata carries the version; nothing is read from pyproject.toml. The watch lasts at least 150 s from the finished upload (from the declaration when no upload was needed) and, once the version carries an `operation_deadline_at`, until that deadline plus 30 s. A version whose `operation_id` no longer matches the declared one was replaced by another publish: it prints that and the `pragma providers versions` pointer, failure. A watch timeout exits 3 with "Admission of <name> <version> has not finished", the status label (`wheel uploaded, waiting for Pragmatiks to record it` for an `awaiting_wheel` version this publish uploaded) and the `pragma providers versions` pointer; an HTTP error while polling prints the API's message and the same pointer, exit 3; a transport error while polling prints what stopped the watch (API unreachable, timeout, dropped connection) and the same pointer, exit 3; any other failure while polling also exits 3. Every exit 3 ends with `To keep waiting, run: pragma providers wait <name> <version> --operation <operation id>`, shell-quoted, naming this publish's operation. A refused declaration is a failure, a 404 included: it prints the API's message with Rich markup escaped (a 401 prints the login-required message); a 503 whose body carries no message prints "Pragmatiks cannot accept the publish right now. Try again later."; every 5xx, a proxy's 502 or 504 included, other than a 503 for an organization that is still being set up or whose setup failed, ends with `To publish it again, run: pragma providers publish --wheel <path> [--changelog <file>]`. A declaration interrupted after connecting prints what broke it off (timeout, dropped connection) and ends with `To publish it again, run: pragma providers publish --wheel <path> [--changelog <file>]`; a declaration whose connection failed, or an invalid one, goes to the global handler. A declaration answer the CLI cannot read prints which fields are invalid, never their values (a whole answer that is not an object prints what is wrong without a field; an upload address that is not an http(s) URL with a host, or upload headers that cannot be sent, is such an answer), or why a body that is not JSON or could not be decoded was refused, and ends with the same publish-again line, failure. A failed upload is a failure, never prints the signed address or the error's own text, and ends with `To publish it again, run: pragma providers publish --wheel <path> [--changelog <file>]`: an expired address prints the SDK's "The wheel upload address expired before storage received the whole wheel (HTTP <status> <code>, storage request <id>).", any other storage refusal the SDK's "Storage refused the wheel upload (HTTP <status> <code>, storage request <id>)." (in both, the code and the request id only when storage sent them), an upload that got no answer although storage may have received the wheel (no answer in time, the connection broke off or closed before an answer, an answer that could not be decoded) "The upload's outcome is unknown (<cause>).", any other upload that got no answer from storage (storage unreachable, sending or the connection timed out, the connection broke off while sending, an invalid request, or any other cause named by its error type) "Could not upload the wheel: <cause>.", and a wheel that cannot be read for the upload "Could not read the wheel to upload it: <reason>."
  - A declaration refused because the organization already has as many provider versions being published at once as Pragmatiks allows, or as many declared wheel bytes in them (409, `detail.limit_name` `unsettled_versions` or `staged_bytes`), prints the API's message, which names the limit and its recovery, with no publish-again line, failure.
  - With `-o json|yaml` the `Published` line goes to stderr too, and once the watch ends stdout carries exactly one document, `{"operation_id": <this publish's operation id>, "version": <the version as last read, a `providers versions -o json` record>}`, on exit 0, exit 1 for a failed or replaced version (replaced when `version.operation_id` differs from `operation_id`), and exit 3; `version` is the latest version a read returned, or the declared version when no read succeeded (without its `wheel_upload`, so the signed upload address is never printed); after a failed read it stays the latest status read successfully, and on exit 3 `version.status` is the declared status only when no read succeeded. Every exit before the watch leaves stdout empty.
- `pragma providers wait <name> <version> --operation <operation id> [-o json|yaml]` - Keep waiting for admission of the publish `--operation` names: requires login, reads `GET /providers/{name}/versions/{version}` once behind a `Reading the version...` spinner (404 prints "Version <version> of provider '<name>' not found.", not found; other API errors go to the global handler), then runs the publish watch from that read, with its outcomes, stdout and stderr: `Published` line and exit 0; failed (the version's `error_message`) or replaced (its `operation_id` differs from `--operation`) exit 1; watch timeout or polling failure exit 3, ending with the same `To keep waiting, run: pragma providers wait ...` line. The watch bound starts at the first read (150 s minimum, or the version's `operation_deadline_at` plus 30 s). A version that already settled is reported at once with its exit code. Status labels are the `providers versions` labels, except `awaiting_wheel`, which shows as publish's watch shows an uploaded wheel: "wheel uploaded, waiting for Pragmatiks to record it". With `-o json|yaml` stdout carries the publish document, `operation_id` being `--operation`.
- `pragma providers versions <name> [-o json|yaml]` - List a provider's versions (columns Version, Status, Published, Package, Wheel SHA-256 shortened to 12 hex characters, the digest of the stored wheel after its rename, not of the built file, Message; `info` shows the same table) with a status label (`awaiting_wheel` waiting for the wheel, its message column, when the version has no message, hinting to run publish again if the publish stopped before its upload finished and that a finished upload shows as wheel received once Pragmatiks records it; `staged` wheel received; `queued` waiting for the provider host; `admitting` admitting; `promoting` publishing to the registry; `published`; `failed`) and the failure message of failed versions
- `pragma providers info <name> [-o json|yaml]` - Show a provider; only a 404 on its versions shows no versions, any other error goes to the global handler
- Every command taking a namespaced provider name (`org/name`) rejects one that is not `org/name` with a usage error before any request
- `pragma providers install <name> [--version <v>]` - Before asking to confirm, print the provider and the version that will install: `--version`, else the stored version (`operation_version`) of a `failed` installation, which installing again without `--version` installs, else the catalog's latest published version. A provider not in the catalog whose versions the caller can read (the author's provider whose only version is still being admitted) previews `latest` and sends the install, whose refusal (409) the global handler prints, failure; a provider with neither a catalog entry nor readable versions prints `Provider '<name>' not found in the store.`, not found.
- `pragma providers install|upgrade|downgrade|uninstall <name>` - Queue the operation and print `Install queued:`, `Upgrade queued:` or `Downgrade queued:` with its target version (`operation_version`), or `Uninstall queued:`, then a dim `Follow it with: pragma providers history <name>` pointer; an uninstall the API refuses with a conflict (resources left without `--cascade`, or an installed provider that embeds it) prints the API's message, failure
- `pragma providers history <name> [-o json|yaml]` - Show an installed provider's history from `GET /providers/installed/{org}/{name}/history`, newest first, with columns Time, Transition (state labels, `Uninstalled` once removed), Operation (`restart` for a host start, as on the web), Version, Message and Cause; kept 30 days, also after an uninstall; no history prints "No history found." in table format
- `pragma providers install|uninstall|upgrade|downgrade|delete <name>` - The preamble before the confirmation (the `Provider:`, `Version:`, `Config:`, `Upgrading:` or `Downgrading:` lines, warnings and the blank line after them) and a declined prompt's `Cancelled.` go to stderr; stdout carries only the result line and the history pointer, or the delete success line
- `pragma providers install <name> [--config KEY=VALUE]... [--config-file <file>]` - `--config` has no short form
- `pragma providers downgrade <name> --version <v>` - A 422 reaches the global API error handler, which prints the API's message; no extra hint
- `pragma providers delete <name> [--yes]` - Delete a provider from the catalog (admins of the owning organization only)

## Organizations
- `pragma organizations me [-o json|yaml]` - Show the caller's organization
- `pragma organizations status [-o json|yaml]` - Show the organization's setup status (`bootstrapping`, `ready`, `failed`)
- `pragma organizations members list [-o json|yaml]` - List the organization's members with columns User ID, Identifier (a dim dash when none) and Role (`admin` or `member`); JSON/YAML records carry `user_id`, `identifier` and `role`; no members prints "No members found." in table format. `pragma auth whoami` prints your own user ID
- `pragma organizations members update <user_id> --role admin|member` - Update a member's role (organization admins only); prints `Updated <user_id>: <role>`
- `pragma organizations members delete <user_id> [--yes|-y]` - Delete a membership (admins delete any, every member their own). Asks `Delete the membership of <user_id>?`; declining prints `Cancelled.` on stderr, success; `--yes` skips the prompt. Deleting your own prints `You left the organization. Run pragma auth login to choose another organization.` and keeps the stored credentials; any other prints `Deleted the membership of <user_id>.`
- Every members command is for a signed-in user: an API key, or a non-admin updating a role or deleting another's membership, is refused (403, failure). An unknown user ID prints the API's message, not found. Demoting or deleting the last admin is refused with `Your organization must keep at least one admin. Promote another member to admin first.` (409, failure). While membership details are unavailable the API's `Membership details are temporarily unavailable. Please try again in a moment.` is printed, failure; the CLI does not retry. Every refusal goes to the global handler

## Accounts
- `pragma accounts delete [--yes|-y]` - Delete your Pragmatiks account and every membership it holds (signed-in users only). Prints `This permanently deletes your Pragmatiks account. You leave every organization you belong to. It cannot be undone.` on stderr and asks `Delete your account?`; declining prints `Cancelled.` on stderr, success; `--yes` skips both. On success prints `Account deleted.` and clears the current context's stored credential when the command used it; a `--token` or `PRAGMA_AUTH_TOKEN` token clears nothing, and other contexts' credentials are kept. The last admin of an organization is refused with `You are the last admin of <slug>[, <slug>…]. Promote another member to admin, or delete the organization first.` (409, failure, through the global handler)

## Exit codes and output streams

The exit-code table lives in `pragma_cli.exit_codes` and prints in `pragma --help`; read it there. This file names outcomes by that table: failure 1, input error 2 (usage errors included), not found 4. A command's own help names only its command-specific codes (`providers publish`, `providers wait`: 3).

Errors and warnings go to stderr; command output, including `-o json`, stays on stdout. With `-o json` or `-o yaml` an empty result prints an empty list; the "No ... found." line is for the table format only. Error reporting lives in `pragma_cli.errors`; the global handler in `main.py` reports what a command does not handle: an API error (status mapped by `compute_http_exit_code`; a 401 prints the login-required message), a request error (failure, with a hint to check the API URL when the API could not be reached), an invalid request such as a token with a line break (failure, printed without the request content), an API URL that is not an `http://`/`https://` URL with a host (input error, naming the context and its URL; checked when the client is built), an API response the CLI cannot read: an invalid model, a body that is not JSON, or a resource schema that is not a valid JSON schema (failure), an unknown context, malformed config or invalid local input (input error), an OS error naming a file (input error), and any other OS error (failure). A broken stdout pipe (`... | head -1`) exits 1 without printing. `errors.report_not_found` prints a command's own 404 message. Missing or conflicting arguments are Click usage errors.

The context (`--context`/`PRAGMA_CONTEXT`) is resolved when a command first needs the API client, so `pragma config` commands work while it names a context that does not exist yet (`PRAGMA_CONTEXT=new pragma config set-context new --api-url ...`).

## Configuration
- `pragma config current-context` - Show the active context (honoring `--context`), its API and Auth URLs, and `Project: <project> (source: --project flag|PRAGMA_PROJECT env var|context default)`, or `Project: none set`
- `pragma projects current [-o table|json|yaml]` - Print the project commands target as `<project> (source: ...)` with the same labels, or `none set`; `-o json|yaml` prints `{"project": <project>|null, "source": <label>|null}`
- In both, a flag or env var project other than the context default also prints `Warning: context '<context>' default project is '<default>'|none set; commands use '<project>' from <source>.` on stderr; success
- `pragma config get-contexts` - List available contexts
- `pragma config use-context <name>` - Switch context; an unknown context (here, in `config delete-context`, `auth login`, `projects use`, or via `--context`/`PRAGMA_CONTEXT` for a command that calls the API) prints "Error: Context '<name>' not found. Available contexts: ..." on stderr, input error
- `pragma config set-context <name> --api-url <url>` - Create/update context; an API URL that is not an `http://`/`https://` URL with a host is a usage error
- `pragma config delete-context <name>` - Delete context; the current context is refused with a pointer to `pragma config use-context`, input error

## Authentication
- `pragma auth login [--context <name>]` - Authenticate (opens browser) and save the token under `<name>` (default: the resolved context); it never switches the active context. When `<name>` is not the configured current context, success also prints `Context '<name>' is not active; run 'pragma config use-context <name>' to activate it.`
- `pragma auth whoami` - Show current user; no token or an expired one is a status report on stdout (success); a token the API rejects or an unreachable API is an error on stderr
- `pragma auth token` - Print the bearer token; without a valid one prints the login-required message on stderr, failure
- `pragma auth logout` - Clear credentials
