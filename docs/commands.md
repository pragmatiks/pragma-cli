# Commands

The behavior contract of every `pragma` command: arguments, output, errors and exit codes. Change it in the same commit as the command.

## Resources
- `pragma resources list [--provider|-p <p>] [--resource|-r <type>] [--tag <t>]... [--health blocked|failed|degraded|healthy] [-o json|yaml]` - List resources in the active project, filtered by provider, resource type, tags (all must match) and health
- `pragma resources schemas [--provider|-p <provider>] [-o json|yaml]` - List available resource schemas with columns Provider, Resource, Serving and Description; Serving is `yes` when Pragmatiks would accept an apply of the type now and a dim `no` while its provider has never served a version, after its installation failed, while it is being uninstalled or while it moves its resources to a new version; JSON/YAML records carry `serving`
- `pragma resources get <org/provider/resource[/name]>` - Get resource(s) by type or full ID
- `pragma resources describe <org/provider/resource/name> [--reveal] [-o json|yaml]` - Show detailed resource info; a `Health` row after State shows the resource's `health` (`healthy`, `blocked`, `failed`, or `degraded — <id> failed`, naming every failed dependency in `degraded_by`, comma-separated), an `Owned by:` section shows its `owner`, the resource that applied it and whose deletion deletes it, as `  <provider>/<resource>/<name>` followed by the owner's `command` dimmed, and a `Blocked by:` section lists each of its `blockers` as `  <id> — <reason>` followed by the blocker's `command` dimmed (an owned resource that failed reads `<id> failed. Apply this resource again to retry it.`), and a `Waiting for provider:` section shows its `provider_blocker`, set while the resource's provider changes version, as `  <provider> — <reason>` followed by its `command` dimmed; each is left out when the API does not send it; a `Provider version` row after `Operation` shows the provider version whose operation produced the outputs, left out when the API sends none
  - Pragmatiks returns every value its resource type's schema marks secret (`format: password`, through `$ref` and `anyOf`/`oneOf`/`allOf`) as `********`, in every output format; in table format a top-level config or output field whose schema is secret carries a dim `[secret]` label, and `[immutable]` marks an immutable config field. `--reveal` (help: `Show secret field values`) asks for the real values. The labels come from the type's schemas (`list_resource_schemas` for the resource's provider); a schema read that fails prints no labels and the details still print
  - `describe -o yaml` piped into `apply` carries `********` into each secret field, and the apply is refused with a 422 naming the field (`Field <path> holds a sensitive value. Reference a secret resource instead of a literal value.`); apply again from the source file, or reference a secret resource
- `pragma resources history <org/provider/resource/name> [-o json|yaml]` - Show a resource's history from `GET /projects/{project_id}/resources/history`, newest first, with columns Time, Transition (raw states, `<from> -> <to>`, the entered state alone for the first row), Operation (the recorded event), Version (the provider version that ran it, a dim dash when none) and Message (the failure message); kept 30 days, also after a delete, and a resource recreated under the same ID shows every lifetime; an ID with no history, one that never existed included, prints "No history found." in table format, success; an unknown project is not found
- `pragma resources vitals <org/provider/resource/name> [-o json|yaml]` - Show the vitals the resource's provider reports from `GET /projects/{project_id}/resources/vitals`, read live from the object the resource manages: a table with a Status row (`nominal` green, `impaired` yellow, `down` red) and a Message row (a dim dash when none), then a `Details:` section listing each provider-specific detail as `  <key>: <value>`, left out when the provider sends none; JSON/YAML print `status`, `message` and `details`; every status is a successful read; a missing resource (404), one not applied yet (409), a provider that is unavailable or cannot report (502) and one that does not report in time (504) go to the global handler, which prints the API's message, failure; distinct from the computed `health` that `describe` shows
- A processing resource holding a configuration applied while its operation runs (`queued_config`) shows its state as `processing (apply queued)` in the `list`/`get` State column, the `describe` State row, the `apply` `Applied <id> [<state>]` line and the `PARTIAL APPLY FAILURE` report's applied list; `describe` also shows an `Operation` row, `<operation type, lowercased> <operation_id>`, while the resource carries an `operation_id`
- `pragma resources logs <org/provider/resource/name> [--since <ISO 8601>] [--tail <1-10000>] [--follow] [-o json|yaml]` - Show a resource's logs from its provider (`GET /projects/{project_id}/resources/logs`), one `<timestamp> <level> <message>` line per entry, never wrapped, oldest first, `--tail` (default 100) most recent entries, only those at or after `--since` when given (a timestamp without an offset is read as UTC); no entries prints "No logs found.", success. JSON/YAML print the list of entries with `timestamp`, `level`, `message` and `metadata`. With `--follow` the `--tail` most recent entries print first, then each new entry as the provider writes it, until the stream ends; with `-o json` each entry prints as one JSON object per line and the end notices go to stderr, and `--follow -o yaml` is a usage error, exit 2; delivery is at most once, with no replay, and order is kept per source but not across sources. A stream that ends prints `Log stream ended: <reason>`, success; on `provider_restarted` (the provider restarted) or `host_draining` (the provider's host restarted) it also prints the last entry's timestamp and to run again with `--follow --since <timestamp>`, noting that entries at that timestamp print again and `--tail` caps how many earlier entries print. An `error` event prints `Log stream failed: <message>` on stderr, failure; a stream that breaks, goes silent past the keep-alive interval or closes without an end or error event prints that the connection was lost, failure; Ctrl-C closes the stream, exit 130 (`INTERRUPTED_EXIT_CODE`). Before the stream opens, a missing resource (404), one not applied yet (409), too many log streams open for this provider (429), a type that does not support following logs (501), a provider that is unavailable (502) and one that does not answer in time (504) go to the global handler, which prints the API's message with its HTTP exit code. Authentication: the active context's credentials, project-scoped
- `pragma resources apply <file>... | -f <file>... [--draft]` - Apply resources from YAML. Every document is sent as `pending`, or as `draft` with `--draft`, whatever its own `lifecycle_state`; the API refuses a draft save of a resource that is neither new nor a draft (409, its message names the recovery). While a provider moves its resources to a new version (installation state Translating), the API refuses an apply or a draft save that writes a resource of that provider with a 409 that the global handler prints unchanged; it names the provider and the target version and ends with the action to repeat, for an apply `<provider> is moving its resources to <version>. Apply again once pragma providers list --installed shows <provider> ready.` Files given both positionally and with `-f` are a usage error. Every document is planned first; invalid documents are listed and the command exits with an input error before anything is applied. A schema read the API refuses (any status but 404, which skips schema validation for that provider), a schema that is not a valid JSON schema, or a broken network goes to the global handler, failure, before anything is applied. A `pragma://files/<name>` reference resolves within the referencing resource's project
  - A `pragma/file` resource whose `config.content` is `@<path>` names a local file, which planning checks without reading it: the path is relative to the manifest's directory, never absolute, never contains `..`, resolves (symlinks followed) inside that directory, and is a regular file opened without following a final symlink; planning records its size and identity (device and inode) and closes it. `config.content_type` is required with `@<path>` and is the upload's media type, and it leaves the applied config. The file uploads under the resource's name, and the applied config's `content` is the file's reference `pragma://files/<name>`, which the resource reads the stored file through. There is no CLI size limit: Pragmatiks refuses a file over its maximum size (413) before any byte is sent. Any other `@<path>` in a config is inlined as UTF-8 text under the same path rules, up to 10 MiB
  - Every planned file is uploaded before any resource is applied, in plan order, into the active project: the file is reopened under the same rules and refused as `<path> was replaced after it was planned.` when its identity changed since planning, then streamed through the SDK's `upload_file` behind an `Uploading <name> (<size>)` spinner on stderr, and `Uploaded <name> (<size>)` prints on stdout once Pragmatiks has stored it (sizes in B, KiB, MiB or GiB). An identical file already stored or being stored is not sent again, so applying again after a failure re-sends nothing that is stored
  - An upload failure prints `Error uploading <name> for <id>: <reason>`, `No resource was applied.` and the command to run next on stderr, never the signed upload address, and exits before any apply: a file that no longer passes the path rules, was replaced after planning, or cannot be read, input error; an API error (413 `file_too_large`, 422 invalid name or declaration, 409 `file_delete_in_progress` while the content of a deleted `pragma/file` resource of that name is still being deleted, 503 `file_upload_unavailable`, with the organization set-up message for an organization not set up yet), the API's message and its status's code; an API answer the CLI cannot read, which fields are invalid and never their values, failure; storage refusing the upload, or the upload ending without the file stored (the file changing while it was uploaded, the upload address expiring, replaced by an upload of other content, failed, deleted since, or another upload of the name still being stored after three minutes), the SDK's message, which ends with `Upload operation <id>.` once the upload was declared, failure; the API unreachable, the API's request-failure phrase, or storage unreachable or breaking off, the storage phrase `providers publish` uses (never the error's own text), failure. Each ends with `To apply again, run: pragma <the same arguments>`, shell-quoted. An upload that reached Pragmatiks and showed no progress for three minutes prints the SDK's message (it may still complete, uploading the same content again keeps waiting without sending it again, and it names the upload operation) and `To keep waiting for it, run: pragma <the same arguments>`, exit 3
  - An apply failure after the uploads prints the `PARTIAL APPLY FAILURE` report on stderr: `Uploaded (<n>)` (the resources whose files are stored), `Applied (<n>)`, `Failed (1)` and `Not attempted (<n>)`; the CLI has no `pragma files` command
- `pragma resources delete|deactivate <org/provider/resource/name> | -f <file>...` - Delete or deactivate a resource. Deleting a `pragma/file` resource deletes its uploaded content shortly afterwards, and deactivating one keeps it; a delete while a new upload of the file is being stored is refused with 409 `file_upload_in_progress`, whose message the CLI prints, and succeeds once the upload is stored. With `-f`, every file is parsed and checked first; a file that is not UTF-8 or valid YAML, or a document without a provider, resource and name or declaring a `project_id` other than the active project, is listed and the command exits with an input error before any resource changes. A resource ID together with `-f` is a usage error. The response's impact prints under `Resources this reaches:` as one `  <id> (<state>) — <action>` line per resource reached, `<state>` being the state it is in before the teardown and `<action>` one of `torn down`, `left in draft`, `moved to waiting until its dependency returns` or `failed, its dependency is deleted`; `--dry-run` prints `Dry run — <id> was not removed.` (or `was not deactivated.`) above those lines and changes nothing, and a refused preview prints the API's message and fails as the real call would
- When `--project` or `PRAGMA_PROJECT` sets a project other than the context default, every project-scoped resource command first prints `Using project '<project>' (source: --project flag|PRAGMA_PROJECT env var; context '<context>' default is '<default>'|none set)` on stderr; with the context default, or an override naming the same project, nothing extra is printed, so the notice has no suppression switch
- `pragma resources tags list/add/remove` - Manage resource tags; `add` and `remove` take `--tag <t>` (repeatable)
- No subcommand option uses a short flag the root command uses (`-c` for `--context`, `-t` for `--token`); `--tag` and `providers install --config` have no short form
- A resource ID that is not `org/provider/resource/name` with no empty segment (`get` also takes `org/provider/resource`) is a usage error before any request, `history` and `vitals` included

## Providers
- `pragma providers list [--scope public|tenant] [--query|-q <q>] [--tags <t1,t2>] [--limit <n>] [--offset <n>] [--installed] [-o json|yaml]` - List providers in the catalog, filtered by scope (`public` or `tenant`), a search query and comma-separated tags, paged by `--limit` (default 20, at most 100) and `--offset` (default 0); an empty table prints `No providers found.`, or `No providers found matching '<q>'.` with `--query`; `--installed` lists installed providers with columns Provider, State (labelled as on the web: Queued, Starting, Draining, Translating, Switching, Running, Failed, Uninstalling), Version (served, a dash before the first ready), Operation (the running operation and its target version, `restart` for a host start, while `operation_running`, a dim dash once it settled) and Message (the failure message); JSON/YAML records carry `installed_version`, the raw `lifecycle_state`, `operation_type`, `operation_version`, `operation_running` and `failure_message`
- `pragma providers init <name> [--directory|-d <path>] [--description <text>] [--author <name>] [--email <email>] [--defaults]` - Initialize a new provider project in `--directory` (default `./<name>-provider`); `-o`/`--output` is not accepted, and `--description` has no short form. The `Creating provider project:` and `Template:` lines and the blank line after the copy go to stderr; stdout carries the `Created provider project:` line and the next steps
- `pragma providers update [project-directory]` - Update project from template
- `pragma providers publish [project-directory | --wheel <path>] [--changelog <file>] [-o json|yaml]` - Publish a new provider version: builds the wheel with `uv build --wheel --out-dir <project-directory>/dist` (so a uv workspace member's wheel lands in its own `dist/`; a project directory that does not exist or has no `pyproject.toml`, a missing `uv`, or a failed build is an input error) unless `--wheel` points at a prebuilt one (passing both is a usage error). All its progress goes to stderr and, in table format (the default), only the final `Published <name> <version> — Python …, SDK …, <n> resource types` line goes to stdout. Once the wheel is built it reads the caller's organization behind a spinner (`GET /organizations/me`, refusals go to the global handler), renames a copy of the wheel behind a `Renaming <filename>...` spinner to the organization's distribution name `<organization>-<provider>` in a `pragma-publish-` temporary directory kept until the upload ends (`pragma_sdk.rename_provider_wheel`; the original file is left unchanged; a wheel already carrying that name, or naming no single provider, is used as is) and prints `Renamed to <filename>` when the filename changed, reads the version's declaration from the renamed copy behind a `Reading <filename>...` spinner (a wheel that cannot be renamed or read, a wheel expanding past the size limit included, exits 2; a built wheel whose reading fails with an operating system error once open prints "Could not read the wheel: <reason>. Check the disk holding the wheel, then publish again.", input error; a renamed copy, or its temporary directory, that cannot be written, or a renamed copy that cannot be read back (an operating system error opening or reading it), prints "Could not write the renamed copy of the wheel: <reason>. Free space in the temporary directory or point TMPDIR elsewhere, then publish again.", failure; the temporary directory is made before the CLI knows whether a copy is needed, so one that cannot be created fails a wheel needing no copy too; a temporary directory that cannot be removed prints "Warning: Could not remove the temporary directory <path>; delete it yourself." and never fails the publish). The organization is read before the wheel, so an unreachable API is reported before an unreadable wheel. It then declares the renamed copy with `POST /providers/publish` (201 new, 200 when the identical declaration is already in flight) and prints `Publishing <name> <version>` and the operation id dimmed. When the declaration returns a `wheel_upload` address (only while the version is `awaiting_wheel`) it PUTs the renamed copy straight to that signed storage address and prints `Uploaded <size>`, or `Wheel already uploaded` when storage already holds it; the watch spinner then starts at `wheel uploaded, waiting for Pragmatiks to record it`, the label it keeps while reads still show `awaiting_wheel`. Without an address it prints `Wheel already received` and a `Status: <label>` line for the declared status, and the spinner starts there. It then polls `GET /providers/{name}/versions/{version}` every 2 s from the declared version, showing the status label beside a spinner and printing a `Status: <label>` line each time a read shows a different status from the previous one, until the organization's provider host admits it (`published`) or fails it (`failed`, prints the version's `error_message`, failure). The wheel alone identifies the version: its `pragma.provider` entry point names the provider and its metadata carries the version; nothing is read from pyproject.toml. The watch lasts at least 150 s from the finished upload (from the declaration when no upload was needed) and, once the version carries an `operation_deadline_at`, until that deadline plus 30 s. A version whose `operation_id` no longer matches the declared one was replaced by another publish: it prints that and the `pragma providers versions` pointer, failure. A watch timeout exits 3 with "Admission of <name> <version> has not finished", the status label (`wheel uploaded, waiting for Pragmatiks to record it` for an `awaiting_wheel` version this publish uploaded) and the `pragma providers versions` pointer; an HTTP error while polling prints the API's message and the same pointer, exit 3; a transport error while polling prints what stopped the watch (API unreachable, timeout, dropped connection) and the same pointer, exit 3; any other failure while polling also exits 3. Every exit 3 ends with `To keep waiting, run: pragma providers wait <name> <version> --operation <operation id>`, shell-quoted, naming this publish's operation. A refused declaration is a failure, a 404 included: it prints the API's message with Rich markup escaped (a 401 prints the login-required message); a 503 whose body carries no message prints "Pragmatiks cannot accept the publish right now. Try again later."; every 5xx, a proxy's 502 or 504 included, other than a 503 for an organization that is still being set up or whose setup failed, ends with `To publish it again, run: pragma providers publish --wheel <path> [--changelog <file>]`. A declaration interrupted after connecting prints what broke it off (timeout, dropped connection) and ends with `To publish it again, run: pragma providers publish --wheel <path> [--changelog <file>]`; a declaration whose connection failed, or an invalid one, goes to the global handler. A declaration answer the CLI cannot read prints which fields are invalid, never their values (a whole answer that is not an object prints what is wrong without a field; an upload address that is not an http(s) URL with a host, or upload headers that cannot be sent, is such an answer), or why a body that is not JSON or could not be decoded was refused, and ends with the same publish-again line, failure. A failed upload is a failure, never prints the signed address or the error's own text, and ends with `To publish it again, run: pragma providers publish --wheel <path> [--changelog <file>]`: an expired address prints the SDK's "The upload address expired before storage received the whole upload (HTTP <status> <code>, storage request <id>).", any other storage refusal the SDK's "Storage refused the upload (HTTP <status> <code>, storage request <id>)." (in both, the code and the request id only when storage sent them), an upload that got no answer although storage may have received the wheel (no answer in time, the connection broke off or closed before an answer, an answer that could not be decoded) "The upload's outcome is unknown (<cause>).", any other upload that got no answer from storage (storage unreachable, sending or the connection timed out, the connection broke off while sending, an invalid request, or any other cause named by its error type) "Could not upload the wheel: <cause>.", and a wheel that cannot be read for the upload "Could not read the wheel to upload it: <reason>."
  - A declaration refused because the organization already has as many provider versions being published at once as Pragmatiks allows, or as many declared wheel bytes in them (409, `detail.limit_name` `unsettled_versions` or `staged_bytes`), prints the API's message, which names the limit and its recovery, with no publish-again line, failure.
  - With `-o json|yaml` the `Published` line goes to stderr too, and once the watch ends stdout carries exactly one document, `{"operation_id": <this publish's operation id>, "version": <the version as last read, a `providers versions -o json` record>}`, on exit 0, exit 1 for a failed or replaced version (replaced when `version.operation_id` differs from `operation_id`), and exit 3; `version` is the latest version a read returned, or the declared version when no read succeeded (without its `wheel_upload`, so the signed upload address is never printed); after a failed read it stays the latest status read successfully, and on exit 3 `version.status` is the declared status only when no read succeeded. Every exit before the watch leaves stdout empty.
- `pragma providers wait <name> <version> --operation <operation id> [-o json|yaml]` - Keep waiting for admission of the publish `--operation` names: requires login, reads `GET /providers/{name}/versions/{version}` once behind a `Reading the version...` spinner (404 prints "Version <version> of provider '<name>' not found.", not found; other API errors go to the global handler), then runs the publish watch from that read, with its outcomes, stdout and stderr: `Published` line and exit 0; failed (the version's `error_message`) or replaced (its `operation_id` differs from `--operation`) exit 1; watch timeout or polling failure exit 3, ending with the same `To keep waiting, run: pragma providers wait ...` line. The watch bound starts at the first read (150 s minimum, or the version's `operation_deadline_at` plus 30 s). A version that already settled is reported at once with its exit code. Status labels are the `providers versions` labels, except `awaiting_wheel`, which shows as publish's watch shows an uploaded wheel: "wheel uploaded, waiting for Pragmatiks to record it". With `-o json|yaml` stdout carries the publish document, `operation_id` being `--operation`.
- `pragma providers versions <name> [-o json|yaml]` - List a provider's versions (columns Version, Status, Published, Package, Wheel SHA-256 shortened to 12 hex characters, the digest of the wheel as stored after its rename, not of the built file, Message; `info` shows the same table) with a status label (`awaiting_wheel` waiting for the wheel, its message column, when the version has no message, hinting to run publish again if the publish stopped before its upload finished and that a finished upload shows as wheel received once Pragmatiks records it; `staged` wheel received; `queued` waiting for the provider host; `admitting` admitting; `promoting` publishing to the registry; `published`; `failed`) and the failure message of failed versions
- `pragma providers info <name> [-o json|yaml]` - Show a provider; only a 404 on its versions shows no versions, any other error goes to the global handler
- Every command taking a namespaced provider name (`org/name`) rejects one that is not `org/name` with a usage error before any request
- `pragma providers install <name> [--version <v>]` - Before asking to confirm, print the provider and the version that will install: `--version`, else a `failed` installation's stored version (`operation_version`), which installing again without `--version` installs, else the catalog's latest published version. A provider not in the catalog whose versions the caller can read (the author's provider whose only version is still being admitted) previews `latest` and sends the install, whose refusal (409) the global handler prints, failure; a provider with neither a catalog entry nor readable versions prints `Provider '<name>' not found in the catalog.`, not found.
- `pragma providers install|upgrade|downgrade|uninstall <name>` - Queue the operation and print `Install queued:`, `Upgrade queued:` or `Downgrade queued:` with its target version (`operation_version`), or `Uninstall queued:`, then a dim `Follow it with: pragma providers history <name>` pointer; an uninstall the API refuses with a conflict (resources left without `--cascade`, or an installed provider that embeds it) prints the API's message, failure
- `pragma providers history <name> [-o json|yaml]` - Show an installed provider's history from `GET /providers/installed/{org}/{name}/history`, newest first, with columns Time, Transition (state labels, `Uninstalled` once removed), Operation (`restart` for a host start, as on the web), Version, Message and Cause; kept 30 days, also after an uninstall; no history prints "No history found." in table format
- `pragma providers install|uninstall|upgrade|downgrade|delete <name>` - The preamble before the confirmation (the `Provider:`, `Version:`, `Config:`, `Upgrading:` or `Downgrading:` lines, warnings and the blank line after them) and a declined prompt's `Cancelled.` go to stderr; stdout carries only the result line and the history pointer, or the delete success line
- `pragma providers install <name> [--config KEY=VALUE]... [--config-file <file>]` - `--config` has no short form
- `pragma providers downgrade <name> --version <v>` - A 422 reaches the global API error handler, which prints the API's message; no extra hint
- `pragma providers delete <name> [--yes]` - Delete a provider from the catalog (admins of the owning organization only)

## Projects
- `pragma projects list [-o table|json|yaml]` - List the projects the caller can see (`GET /projects`) with columns ID, Name, Organization ID and Updated; JSON/YAML records carry `project_id`, `organization_id`, `name`, `created_at` and `updated_at`; no projects prints "No projects found." in table format (JSON/YAML print an empty list)
- `pragma projects get <project_id> [-o table|json|yaml]` - Show one project (`GET /projects/{project_id}`) as ID, Name, Organization ID, Created and Updated rows; JSON/YAML print a one-record list with the `list` fields
- `pragma projects create <name>` - Create a project (`POST /projects`); prints `Created project: <name> (<project_id>)`. It does not make the new project the context default; run `projects use` for that
- `pragma projects update <project_id> --name <name>` - Rename a project (`PATCH /projects/{project_id}`); `--name` is required; prints `Updated project: <name> (<project_id>)`
- `pragma projects delete <project_id> [--yes --confirm <name>] [--orphan-resources]` - Delete a project (`DELETE /projects/{project_id}`) after typed confirmation of its name. It first reads the project (`GET /projects/{project_id}`). Without `--yes` it prompts `Type the project name to confirm deletion: `; with `--yes` the name comes from `--confirm`. `--yes` without `--confirm`, or `--confirm` without `--yes`, is a usage error; neither has a short form. A value that is not the project's exact name prints `Confirmation did not match the project name '<name>'. Type the name exactly, or pass --yes --confirm <name>.` on stderr, input error, and nothing is deleted. A project that still holds resources is refused (409): stderr prints `Project <project_id> still contains <n> resource(s).`, up to 20 of their IDs (under `Showing <shown> of <n>:` when the list is cut, else `Resources:`), then the two ways out, deleting the resources with `pragma resources delete <org/provider/resource/name>` or running again with `--orphan-resources`; with `--orphan-resources` already given it names only the first; failure. `--orphan-resources` deletes the project but leaves its resources and their infrastructure running outside Pragmatiks; without `--yes` it first prints a warning on stderr that billing continues. Success prints `Deleted project: <name>`, or `Deleted project tracking: <name>` and `Resources were not touched and continue to run outside Pragmatiks.` with `--orphan-resources`
- `pragma projects use <project_id>` - Save `<project_id>` as the default project of the resolved context (`--context`/`-c`/`PRAGMA_CONTEXT`, else the current context) in the config file; it makes no request, so the project is not checked. Prints `Current project for context '<context>': <project_id>`; an unknown context is an input error
- `pragma projects current [-o table|json|yaml]` - Show the project commands target and where it comes from, in precedence order: the global `--project` flag, `PRAGMA_PROJECT`, then the context default. The table prints `<project> (source: --project flag|PRAGMA_PROJECT env var|context default)`, or `none set`; JSON/YAML print `{"project": ..., "source": ...}`, both null when none is set. When a flag or variable sets a project other than the context default it also prints `Warning: context '<context>' default project is '<default>'|none set; commands use '<project>' from <source>.` on stderr. It makes no request and succeeds whatever is set; an unknown context is an input error
- Every command but `use` and `current` calls the API: no credentials, or a token the API refuses, prints the login-required message, failure; an unknown project prints the API's message, not found; other refusals go to the global handler

## Organizations
- `pragma organizations me [-o table|json|yaml]` - Show the caller's organization from `GET /organizations/me`, which answers only once the organization is set up. The table prints an `Organization` heading, then `ID:`, `Name:`, `Slug:`, `Status:` (always `ready`, since only a ready organization answers) and `Created:` and `Updated:` (ISO 8601); JSON/YAML carry `organization_id`, `name`, `slug`, `status`, `created_at` and `updated_at`. No credentials prints the login-required message, failure. While the organization is being set up, or its record does not exist yet, prints `Your organization is being set up. Please try again in a moment.` (503, failure); after a failed setup, `Your organization could not be set up. Please contact support at support@pragmatiks.io.` (503, failure); an organization being deactivated prints `Error: Your organization is being deactivated and is no longer available.` and a deleted one `Error: Your organization has been deleted and is no longer available.` (410, failure); a record gone between the check and the read prints the API's message, not found (404). Other refusals, such as an API key not scoped to an organization (403), go to the global handler, failure
- `pragma organizations status [-o table|json|yaml]` - Show the organization's setup status from `GET /organizations/me/status`. The table prints an `Organization Status` heading and `Status: <bootstrapping|ready|failed>`; JSON/YAML carry `{"status": ...}`. An organization whose record does not exist yet reads `bootstrapping`; a failed setup, a deactivating and a deleted organization read `failed`. It never gives the setup refusal, so it is safe to poll, and it succeeds whatever the status. No credentials prints the login-required message, failure; other refusals go to the global handler, failure
- `pragma organizations members list [-o table|json|yaml]` - List the organization's members with columns User ID, Identifier (a dim dash when none) and Role (`admin` or `member`); JSON/YAML records carry `user_id`, `identifier` and `role`; no members prints "No members found." in table format. `pragma auth whoami` prints your own user ID, or use `pragma organizations members leave` to leave without it
- `pragma organizations members update <user_id> --role admin|member` - Update a member's role (organization admins only); prints `Updated <user_id>: <role>`
- `pragma organizations members delete <user_id> [--yes|-y]` - Delete a membership (admins delete any, every member their own). Asks `Delete the membership of <user_id>?`; declining prints `Cancelled.` on stderr, success; `--yes` skips the prompt. Deleting your own prints `You left the organization. Run pragma auth login to choose another organization.` and keeps your stored credentials; any other prints `Deleted the membership of <user_id>.`
- `pragma organizations members leave [--yes|-y]` - Leave the organization by deleting your own membership, without a user ID. Asks `Leave the organization?`; declining prints `Cancelled.` on stderr, success; `--yes` skips the prompt. On success prints `You left the organization. Run pragma auth login to choose another organization.` and keeps your stored credentials. It has no route of its own: it deletes your own membership exactly like `members delete <your user ID>`, through the same API call, so errors and exit codes match
- Every members command is for a signed-in user: an API key, or a non-admin updating a role or deleting another's membership, is refused (403, failure). An unknown user ID prints the API's message, not found. Demoting or deleting the last admin is refused with `Your organization must keep at least one admin. Promote another member to admin first.` (409, failure). While membership details are unavailable the API's `Membership details are temporarily unavailable. Please try again in a moment.` is printed, failure; the CLI does not retry. Every refusal goes to the global handler

## Accounts
- `pragma accounts delete [--yes|-y]` - Delete your Pragmatiks account and every membership it holds (signed-in users only). Prints `This permanently deletes your Pragmatiks account. You leave every organization you belong to. It cannot be undone.` on stderr and asks `Delete your account?`; declining prints `Cancelled.` on stderr, success; `--yes` skips both. On success prints `Account deleted.` and clears the current context's stored credential when the command used it; a `--token` or `PRAGMA_AUTH_TOKEN` token clears nothing, and other contexts' credentials are kept. The last admin of an organization is refused with `You are the last admin of <slug>[, <slug>…]. Promote another member to admin, or delete the organization first.` (409, failure, through the global handler)

## API keys
- `pragma api-keys create <name> [-o table|json|yaml]` - Create an API key for the organization (`POST /api-keys`). In every format it prints `Created API key <name> (<id>) in context '<context>'` on stderr, naming the resolved context the key was created through. The table prints only the raw secret on stdout, so `SECRET=$(pragma api-keys create <name>)` captures it; JSON/YAML print the one record `id`, `name`, `created_at` and `secret`. It then prints `Store this secret now: Pragmatiks never shows it again.` on stderr; the secret is never printed again, by this or any other command
- `pragma api-keys list [-o table|json|yaml]` - List the organization's active API keys (`GET /api-keys`) with columns ID, Name, Created and Last used (ISO 8601; a dim dash when never used); the ID is never cut at any terminal width, since `revoke` takes it whole, and the other columns fold onto more lines instead; JSON/YAML records carry `id`, `name`, `created_at` and `last_used_at`, never a secret; no keys prints "No API keys found." in table format
- `pragma api-keys revoke <api_key_id> [--yes|-y]` - Revoke an API key (`DELETE /api-keys/{id}`), so it no longer authenticates; a revoked key keeps its name, which stays taken. Asks `Revoke the API key <api_key_id>?`; declining prints `Cancelled.` on stderr, success; `--yes` skips the prompt. On success prints `Revoked <api_key_id>.`
- `list` works for any member of the organization and for an API key. `create` and `revoke` are for an organization admin signed in as a user: an API key, or a non-admin, is refused (403, failure). An unknown key, or another organization's, prints the API's message, not found. A name the organization has, or once had, is refused (409, failure). No credentials prints the login-required message, failure. Every refusal goes to the global handler

## Exit codes and output streams

The exit-code table lives in `pragma_cli.exit_codes` and prints in `pragma --help`; read it there. This file names outcomes by that table: failure 1, input error 2 (usage errors included), not found 4, interrupted 130. A command's own help names only its command-specific codes (`providers publish`, `providers wait`, `resources apply`: 3, `UNCONFIRMED_EXIT_CODE`: what the command sent is not confirmed yet and may still complete).

Errors and warnings go to stderr; command output, including `-o json`, stays on stdout. With `-o json` or `-o yaml` an empty result prints an empty list; the "No ... found." line is for the table format only. Error reporting lives in `pragma_cli.errors`; the global handler in `main.py` reports what a command does not handle: an API error (status mapped by `compute_http_exit_code`; a 401 prints the login-required message), a request error (failure, with a hint to check the API URL when the API could not be reached), an invalid request such as a token with a line break (failure, printed without the request content), an API URL that is not an `http://`/`https://` URL with a host (input error, naming the context and its URL; checked when the client is built), an API response the CLI cannot read: an invalid model, a body that is not JSON, or a resource schema that is not a valid JSON schema (failure), an unknown context, malformed config or invalid local input (input error), an OS error naming a file (input error), and any other OS error (failure). A broken stdout pipe (`... | head -1`) exits 1 without printing. `errors.report_not_found` prints a command's own 404 message. Missing or conflicting arguments are Click usage errors.

The context (`--context`/`PRAGMA_CONTEXT`) is resolved when a command first needs the API client, so `pragma config` commands work while it names a context that does not exist yet (`PRAGMA_CONTEXT=new pragma config set-context new --api-url ...`).

## Configuration
- `pragma config current-context` - Show the active context (honoring `--context`), its API and Auth URLs, and `Project: <project> (source: --project flag|PRAGMA_PROJECT env var|context default)`, or `Project: none set`
- `pragma projects current [-o table|json|yaml]` - Print the project commands target as `<project> (source: ...)` with the same labels, or `none set`; `-o json|yaml` prints `{"project": <project>|null, "source": <label>|null}`
- In both, a flag or env var project other than the context default also prints `Warning: context '<context>' default project is '<default>'|none set; commands use '<project>' from <source>.` on stderr; success
- `pragma config get-contexts` - List available contexts
- `pragma config use-context <name>` - Switch context; an unknown context (here, in `config delete-context`, `auth login`, `projects use`, or via `--context`/`PRAGMA_CONTEXT` for a command that calls the API) prints "Error: Context '<name>' not found. Available contexts: ..." on stderr, input error
- `pragma config set-context <name> --api-url <url>` - Create/update context; an API URL that is not an `http://`/`https://` URL with a host is a usage error
- `pragma config delete-context <name>` - Delete context; the current context is refused with a pointer to `pragma config use-context`, input error

## Authentication
- `pragma auth login [--context <name>] [--org <slug> | --with-token]` - Authenticate (opens browser) and save the token under `<name>` (default: the resolved context); it never switches the active context. When `<name>` is not the configured current context, success also prints `Context '<name>' is not active; run 'pragma config use-context <name>' to activate it.` The `Authenticating for context:` and `API URL:` lines, and the browser login's `Opening browser to:` and waiting lines, go to stderr; stdout carries the success lines. With `--with-token` it opens no browser and no callback server: it reads one session token, the JWT sign-in issues, from a pipe on stdin, never from an argument; an API key is a bearer token too but is never saved, `--token` or `PRAGMA_AUTH_TOKEN` passes it per command. Each of these prints its message and is an input error, with nothing saved: stdin is a terminal (`--with-token reads a session token from stdin, but stdin is a terminal. Pipe the token in.`), stdin is empty or only whitespace (`--with-token reads a session token from stdin, but stdin was empty.`), stdin holds more than one whitespace-separated value (`--with-token reads one session token from stdin, but stdin held more than one.`), the value is not a JWT, such as an API key (`--with-token takes a session token. Pass an API key with --token or PRAGMA_AUTH_TOKEN.`), or it is an expired JWT, or one whose `exp` is not a number (`--with-token read an expired session token. Pipe in a fresh one.`). It then checks the token with `GET /auth/me` against `<name>`'s API URL: a 401 prints `The API of context '<name>' refused the session token from stdin; nothing was saved.`, failure; any other refusal goes to the global handler, and nothing is saved. On success it saves the token and prints the same lines as browser login. `--with-token` with `--org` is a usage error, since the token carries its organization
- `pragma auth whoami` - Show current user; no token or an expired JWT is a status report on stdout (success); a token that is not a JWT, such as an API key from `--token` or `PRAGMA_AUTH_TOKEN`, is never judged expired locally and goes to the API; a token the API rejects or an unreachable API is an error on stderr
- `pragma auth token` - Print the bearer token, an API key from `--token` or `PRAGMA_AUTH_TOKEN` included; no token or an expired JWT prints the login-required message on stderr, failure
- `pragma auth logout` - Clear credentials
